# kulman

**kulman** читається «кульман»: кульман — креслярська дошка конструкторського бюро; тут це вхідні
двері набору: він встановлює інструменти й налаштовує проєкт.

`kulman` встановлює, оновлює й налаштовує модулі набору kulman: `kalka` (вікі проєкту для агентів,
що пишуть код) і `plaz` (блок-схеми рішень). Це інсталятор, а не модуль. Реліз 0.7.0 — перший, що
його містить; весь набір описано в [README репозиторію](../../README.uk.md).

## Як отримати

    curl --proto '=https' --tlsv1.2 -sSfL https://github.com/bambooplanedev/kulman/releases/latest/download/install.sh | sh

`install.sh` читає `SHA256SUMS` останнього релізу, завантажує архів `kulman` для цієї машини
(`aarch64-apple-darwin` або `x86_64-unknown-linux-musl`; на будь-якій іншій системі — «no build»),
перевіряє його за цим файлом і кладе бінарник у `~/.kulman-home/bin/kulman`. Йому потрібні `curl`,
`tar`, `mktemp` і `sha256sum` або `shasum`; без інструмента для контрольних сум він зупиняється, а
не пропускає перевірку. Крім цього бінарника й тек, у яких він лежить, `install.sh` нічого не
записує і не змінює профілів оболонки. За будь-якої помилки він виходить з ненульовим кодом і не
лишає тимчасової теки; перше встановлення також не лишає `kulman` у `bin/` (поверх наявного
встановлення лишається старий), а домашню теку, яку він створив, знову видаляє, якщо вона порожня.
Поверх наявного встановлення (є `state.json`) він наприкінці радить запустити `kulman update`, який
доводить модулі до версії щойно покладеного `kulman`. Збірка для Linux статична й працює однаково на
системах із glibc і з musl.

Те саме вручну: завантажте `kulman-v<version>-<target>.tar.gz` і `SHA256SUMS` зі сторінки релізу,
потім

    grep kulman-v<version>-<target>.tar.gz SHA256SUMS | sha256sum -c -   # на macOS: … | shasum -a 256 -c -
    tar -xzf kulman-v<version>-<target>.tar.gz kulman
    mkdir -p ~/.kulman-home/bin && mv kulman ~/.kulman-home/bin/

Далі самі додайте `~/.kulman-home/bin` у `PATH` (агенти запускають `kalka` за назвою) і виконайте:

    ~/.kulman-home/bin/kulman install       # kulman і модулі релізу за замовчуванням
    cd your-project
    kulman setup --scope local         # власний setup кожного встановленого модуля, у цьому проєкті

## Що де лежить

Усе лежить у `~/.kulman-home` (або в `KULMAN_HOME`, якщо задано):

- `bin/kulman` і `bin/<module>` для кожного встановленого модуля;
- `manifest.json` — маніфест установленого релізу;
- `state.json` — установлена версія й модулі, записується останнім (файл, який не є файлом стану,
  записаним kulman, зупиняє кожну команду, і вона його називає: виправте його або видаліть і
  запустіть `kulman install`; файл, який не вдається прочитати, зупиняє її зі шляхом і причиною);
- `.lock` — його тримає команда, що виконується; встановлення, яке не вдалося там, де нічого не
  встановлено, знову видаляє його, якщо саме його створило, і теку теж, якщо саме її створило:
  знайдену домашню теку воно лишає як була.

Батьківська тека цієї теки має існувати; створюється лише сама тека. `bin`, що є симлінком або не є
текою, відхиляється. Жоден профіль оболонки не змінюється.

## Команди

    kulman [status]

Без команди або з `status`: установлена версія й модулі (модуль, бінарника якого немає, позначено
`(missing: run kulman update)`), два рядки `<home>/bin is not on PATH; add it:` і `    export PATH="<home>/bin:$PATH"`, коли теки там
немає (запис у `PATH`, що веде до `bin/` через символічне посилання, зараховується), і чи є новіший реліз. Команда лише читає: нічого не створюється. Хост релізів має 5 с на
зʼєднання й 8 с загалом; якщо їх забракло або сталася будь-яка помилка, останній рядок каже, до чого
не вдалося достукатися і чому.

    kulman install [--modules <MODULES>] [--version <X.Y.Z>] [--yes]

Встановлює kulman і названі модулі (через кому; пробіли навколо назви ігноруються) разом із модулями,
яких вони потребують. Без `--modules` встановлює модулі, які реліз позначає як модулі за
замовчуванням; щоб пропустити якийсь, назвіть решту. `--version` встановлює вказаний реліз замість
останнього. Повторний запуск з іншими модулями додає їх у вже встановленій версії й повертає кожен
бінарник зі списку, якого бракує в `bin/`; встановлений `bin/kulman` тоді лишається як є
(`kulman update` замінює його завжди). Файл `bin/<module>`, якого `state.json` не перелічує, ніколи
не вважається встановленим: його замінює завантажений і перевірений модуль. Коли є новіший реліз,
команда однаково встановлює в уже встановленій версії й каже про це (`newer release X.Y.Z: kulman
update`); коли останній реліз не вдається прочитати, каже про це (`could not check for a newer
release (<base>: <reason>)`). Установлену версію читає, коли вже тримає `.lock`. Якщо встановлена
версія відрізняється від `--version` або новіша за останній реліз, команда нічого не змінює й
виходить з кодом 1: для старішої радить запустити `kulman update`; для новішої — `kulman remove`, а
потім `kulman install --version <X.Y.Z>`. Успішне встановлення закінчується наступними кроками:
ті самі два рядки для `bin/`, якщо її немає в `PATH`, а потім `kulman setup` у проєкті. Коли робити нічого,
команда нічого не записує й натомість каже `already installed: <names> (<version>)` (і, як вище,
про новіший реліз).

    kulman update [--yes]

Оновлює kulman і всі встановлені модулі до останнього релізу — усе або нічого. Реліз, старіший за
встановлений, не встановлюється: нічого не змінюється.

    kulman remove [--modules <MODULES>] [--yes]

Видаляє названі модулі; без `--modules` — усі модулі, сам kulman, його маніфест, стан і lock, потім
`bin/` і домашню теку, якщо вони порожні. Видаляється лише те, що перелічує `state.json`; будь-який
інший файл лишається (без `state.json` не видаляється взагалі нічого, а `bin/kulman`, покладений
`install.sh`, команда називає, щоб ви видалили його самі). Кожен шлях перевіряється до видалення
першого: тека на місці бінарника або будь-що, крім звичайного файлу, на місці `manifest.json` чи
`state.json` зупиняє команду, нічого не видаливши (код виходу 1); так само діє модуль, якого вимагає
інший встановлений (`kulman: cannot remove <a>: <b> requires it`; назвіть обидва, щоб видалити
обидва). `kulman` — не модуль: `--modules kulman` — помилка використання. У терміналі команда спершу
питає (за замовчуванням — ні); без термінала їй потрібен `--yes`, інакше вона нічого не змінює й
виходить з кодом 2. Коли видаляється все, а kalka встановлено, команда ще й каже, що проєкти,
налаштовані через kulman, досі називають `kalka` у конфігах агентів, і спершу в них треба запустити
`kulman setup --remove`: у терміналі — перед питанням, інакше — останнім рядком.

    kulman setup [--modules <MODULES>] [--memory | --no-memory] [--agent <LIST>]
                 [--scope repo|local] [--no-hook] [--remove] [--yes]

Запускає власний `setup` кожного вибраного модуля (`~/.kulman-home/bin/<module> setup …`) у поточній
теці, у порядку релізу: кожен вибраний модуль запускається, хоч би що повернули попередні. Без
`--modules` налаштовуються всі встановлені модулі. `--scope` іде кожному модулю; `--agent`,
`--no-hook` і `--memory`/`--no-memory` належать kalka, і коли kalka не вибрано, це помилка
використання. Памʼять агента ввімкнена, хіба що передано `--no-memory` або її вимикає реліз.
`--remove` скасовує setup кожного модуля. Перед запуском першого модуля бінарник кожного вибраного
модуля має лежати в `bin/` і бути виконуваним; коли не встановлено жодного модуля, налаштовувати
нічого (код виходу 1). Модулі пишуть у власну теку проєкту `.kulman/`: setup відмовляється (код
виходу 1) працювати там, де ця тека — домашня тека kulman (`KULMAN_HOME`, заданий як
`<project>/.kulman`). Коли `bin/` немає в `PATH`, модулі запускаються з нею першою у власному `PATH`
(середовище самого kulman і ваша оболонка не змінюються; шлях `bin/` із `:` не може стояти в `PATH`,
тож тоді їхній `PATH` лишається як є), а setup для kalka спершу пише в stderr тими самими двома рядками, що `bin/` немає в
`PATH` і що додати, а потім, що конфіги агентів, які він пише, запускають `kalka` за назвою.

## Коли kulman питає, а коли ні

Люди й агенти користуються тими самими командами. Команда питає лише тоді, коли і stdin, і stdout —
термінали, а `--yes` не задано; інакше вона нічого не питає й застосовує значення за замовчуванням
(`install`: те, що реліз має за замовчуванням; `setup`: усі встановлені модулі, памʼять увімкнена).
Значення, що не має замовчування, тоді треба передати прапорцем: `kulman setup` без термінала
потребує `--scope`. Коли kulman не питає, модулі, які він запускає, не отримують вводу, тож теж
нічого не питають. `remove`, чиє питання за замовчуванням має відповідь «ні», без термінала нічого
не робить, якщо не передано `--yes`. Підтвердження kulman питає, коли команда вже тримає `.lock` і
прочитала стан, тож показане — це саме те, що буде зроблено. Назви, введені у відповідь на питання,
зіставляються без огляду на регістр.

## Коди виходу

- `0` — зроблено, або робити нічого.
- `1` — помилка; повідомлення каже, що сталося (для завантаження — що саме й звідки). Невдалий
  `install` чи `update`, що нічого не змінив, закінчується рядком `nothing changed`.
- `2` — помилка використання (невідомий прапорець, порожня чи неправильна назва в `--modules` або
  назва, якої реліз не має, відсутній `--scope`, неправильний `KULMAN_RELEASE_URL`, `remove` без
  термінала й без `--yes`).

Кожен модуль, чий setup не вдався, отримує рядок `kulman: <module> setup failed (exit N)` (або
`(signal N)`); решта однаково запускаються. Потім `kulman setup` друкує `kulman: setup finished with
errors: <modules>` і виходить з кодом першого модуля, що не вдався (1, якщо його вбив сигнал).

## Змінні середовища

- `KULMAN_HOME` — домашня тека (за замовчуванням `$HOME/.kulman-home`; порожнє значення — те саме,
  що не задане).
- `KULMAN_RELEASE_URL` — де лежать релізи (за замовчуванням
  `https://github.com/bambooplanedev/kulman/releases`): `https://…` або `file://…`, і більше нічого.

## Один запуск за раз і переривання

Команда, що змінює `~/.kulman-home`, тримає `.lock`, зокрема поки питає; друга чекає на неї й один
раз каже про це в stderr: `kulman: waiting for another kulman run (<home>/.lock)`. Завантаження
перевіряються й розпаковуються в тимчасову теку в домашній (`.tmp-<pid>`), перш ніж щось у `bin/`
зміниться; потім бінарники перейменовуються в `bin/` (kulman — останнім), далі `manifest.json`, далі
`state.json`.

- Перерване до цього моменту встановлення чи оновлення лишає тільки свою тимчасову теку, яку видаляє
  наступний запуск, що знайде `state.json` (домашню теку без нього не прибирають ніколи).
- Перерване під час перейменування, воно лишає частину бінарників у новій версії, а `state.json`
  досі називає стару. `kulman update` встановлює весь реліз заново.
- Бінарник, який `state.json` перелічує, а в `bin/` його немає (перерваний `remove` чи файл,
  видалений вручну), повертають `kulman update` або `kulman install`, а відсутній `manifest.json` —
  `kulman update`; `kulman setup` натомість каже про це й не запускається.

## Будова релізу

Реліз містить у `<base>/download/v<version>/`:

- `manifest.json` — єдине джерело правди про реліз для kulman;
- `<module>-v<version>-<target>.tar.gz` і `kulman-v<version>-<target>.tar.gz`, у кожному один файл,
  названий за своїм бінарником;
- `SHA256SUMS` — рядки `<sha256>  <file>`, для `install.sh` і для людей;
- `install.sh`.

`<base>/latest/download/` віддає ті самі файли останнього релізу. kulman читає маніфест звідти; з
`download/v<version>/` — з `--version`; і з `download/v<installed>/` — для `install` поверх
установленої версії, коли останній реліз новіший або його не вдається прочитати. Кожен архів він
читає з `download/v<version>/`. `install.sh` читає `SHA256SUMS` з `latest/download/`.

`manifest.json`:

```json
{
  "version": "0.7.0",
  "modules": [
    {
      "name": "kalka",
      "summary": "the project wiki for coding agents",
      "default": true,
      "requires": [],
      "options": [{ "name": "memory", "default": true }],
      "archives": {
        "aarch64-apple-darwin": { "file": "kalka-v0.7.0-aarch64-apple-darwin.tar.gz", "sha256": "…" }
      }
    }
  ],
  "kulman": {
    "archives": {
      "aarch64-apple-darwin": { "file": "kulman-v0.7.0-aarch64-apple-darwin.tar.gz", "sha256": "…" }
    }
  }
}
```

Невідомі поля ігноруються. Кожен архів перевіряється за своїм `sha256`, перш ніж його розпакувати.
