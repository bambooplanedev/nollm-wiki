# `wiki`

**Карта вашого проєкту для агентів, що пишуть код: де лежить кожна функція, хто її викликає і які рядки читати. Без жодної LLM під час компіляції.**

`wiki` — модуль [проєкту nollm-wiki](../../README.uk.md), а цей крейт — бінарник `wiki` і бібліотека,
яку він обгортає.

`wiki` компілює проєкт — код, нотатки, документацію — у вікі з перехресними посиланнями в Markdown
і карту символів з діапазонами рядків, а потім віддає її агентам через MCP. Агент питає `search`,
де щось лежить, і отримує рядки `path:start-end`, питає `callers`, хто викликає функцію, і читає
здебільшого саме ці рядки, а не шукає через grep і не відкриває файли цілком. Під час компіляції жодна модель
не викликається: той самий вхід дає побайтово той самий результат на будь-якій машині.

Це не семантичний пошук: зіставлення лексичне, за іменами, словами та імпортами. І не мовний сервер:
виклики розвʼязуються за іменем і кількістю аргументів, без типів.

У прикладах довгі рядки скорочено, пропуски позначено `…`, а рядок із `└` підписує частини
рядка над ним; це не вивід команди.

```
$ wiki callers calls.rs resolve_calls --dir .nollm-wiki
callers of resolve_calls  crates/wiki/src/calls.rs:197-264 — 1 functions in 1 files
crates/wiki/src/lib.rs
  145-464  fn  compile_inner  calls resolve_calls at 329
  └ рядки функції             └ рядок виклику
```

## Можливості

- **Пошук символів.** `search` ранжує сторінки за іменами, словами, документацією та імпортами,
  слово запиту, що є іменем файлу чи кінцем шляху (`strategy_config.h`, `manager/mod.rs`), піднімає цей файл,
  а під кожною сторінкою коду показує функції й типи, що збіглися, у вигляді
  `path:start-end  name  signature — doc`.
- **Структура файлів.** `page` друкує по рядку на кожен символ файлу з його діапазоном рядків, тож
  агент читає сорок рядків замість чотирьох тисяч.
- **Виклики в обидва боки.** `callers` показує функції, які викликають функцію, з рядками кожного
  виклику; `neighbors --symbol` (CLI; MCP з `--tools`) — усе, що функція
  викликає, рівень за рівнем.
- **MCP-сервер.** `wiki serve --source .` компілює проєкт, перекомпільовує його після правок і віддає
  `search`, `page` і `callers` (`neighbors` і `lint` з `--tools`) у Claude Code, pi, Cursor, Codex
  чи будь-який MCP-клієнт.
  Кілька серверів на одному `.nollm-wiki` — це нормально: один компілює, решта віддають те, що він записав.
- **Налаштування однією командою.** `wiki setup` встановлює сервер і те, що каже агентові ним
  користуватися, для Claude Code, pi, Cursor і Codex, а з `--hook` — і хук, що додає до кожного
  запиту відповідні рядки коду.
- **Памʼять агента.** Нотатки з `.agents/memory/` і з тек, у які агенти вже пишуть самі (поки що
  Claude Code), стають сторінками для пошуку, що йдуть після знайденого коду, з датами, псевдонімами
  та `supersedes:`.
- **Мови.** Rust, Python, C і C++ (`.c`, `.h`, `.cpp`, `.cc`, `.cxx`, `.hpp`, `.hh`, `.hxx`; підключувані фрагменти `.inl`, `.ipp` і `.tcc` сторінки не отримують), Go, JavaScript (`.js`, `.mjs`, `.cjs`), TypeScript (з JSX/TSX), скрипти `.vue` і
  `.svelte`, shell (`.sh`, `.bash` або без розширення з shebang `sh`/`bash`: функції, а також змінні UPPERCASE верхнього рівня, які знаходить пошук за точним іменем), Markdown і простий текст.
- **Детермінізм.** Побайтово однаковий результат між запусками, машинами й кількістю потоків;
  інкрементальна перекомпіляція.
- **Відкривається в Obsidian.** Сторінки посилаються одна на одну вікі-посиланнями Obsidian, тож
  тека з результатом — це сховище з робочим графом і зворотними посиланнями; див.
  [що не переноситься](#obsidian-і-quartz).

## Вимоги

- macOS на Apple silicon (`aarch64-apple-darwin`) або Linux x86_64 (`x86_64-unknown-linux-musl`) для
  релізного бінарника. Збірка для Linux статична й працює однаково на системах із glibc і з musl.
- Або Rust 1.90 чи новіший, щоб зібрати з коду (для `cargo test` потрібні ще й `git`, `jq` та
  користувач без прав root). На Windows не перевірено.
- Для агентів: MCP-клієнт — Claude Code, pi, Cursor, Codex, Claude Desktop чи інший. `wiki setup --scope local`
  для Claude Code також потребує CLI `claude` у `PATH`.

## Встановлення

Реліз nollm-wiki містить `wiki` для двох систем, названих вище; на будь-якій іншій збирайте з
вихідного коду.

### Через nollm-wiki

`nollm-wiki-install` встановлює, оновлює й налаштовує `wiki` разом з іншими модулями; кроки описано в
[README репозиторію](../../README.uk.md#встановлення). Коротко, коли `nollm-wiki-install` уже є на машині:

    nollm-wiki-install install                     # модулі релізу за замовчуванням, у ~/.nollm-wiki-home/bin
    cd your-project
    nollm-wiki-install setup --scope local         # запускає тут wiki setup і plaz setup
    nollm-wiki-install update                      # згодом: усе до останнього релізу

Додати `~/.nollm-wiki-home/bin` у свій `PATH` необов'язково, це для набору `nollm-wiki-install` у терміналі (агенти
знаходять `wiki` і без цього; коли `~/.local/bin` у `PATH`, install лінкує туди інструменти). За замовчуванням усе ввімкнено; вимикайте прапорцями
(`nollm-wiki-install install --modules wiki`, `nollm-wiki-install setup --no-memory`). `nollm-wiki-install setup` запускає кожен
вибраний модуль, навіть коли якийсь завершився з помилкою, і наприкінці називає ті, що не вдалися.
`nollm-wiki-install remove` видаляє те, що встановив nollm-wiki (без термінала потрібен `--yes`); проєкти,
налаштовані через nollm-wiki, лишають `wiki` у конфігах агентів, тож спершу запустіть у них
`nollm-wiki-install setup --remove` з тим самим `--scope`. Команди, коди виходу й будова релізу:
[crates/nollm-wiki-install/README.uk.md](../nollm-wiki-install/README.uk.md).

### З коду

    git clone https://github.com/bambooplanedev/nollm-wiki
    cd nollm-wiki
    cargo install --path crates/wiki      # у ~/.cargo/bin

## Швидкий старт

У проєкті, в якому мають орієнтуватися агенти:

    cd your-project
    wiki setup --scope local      # компілює .nollm-wiki, встановлює MCP-сервер і (для pi) скіл

Далі запустіть у цій теці Claude Code або pi: інструменти `wiki` вже там, а сервер тримає `.nollm-wiki/`
в актуальному стані після ваших правок. `--scope repo` натомість пише закомічені файли для всієї
команди, а `wiki setup --remove` з тим самим `--scope` це скасовує. Cursor і Codex:
`wiki setup --agent cursor,codex`; інші клієнти — див. [Агенти](#агенти).

## Використання

### Агенти

Агент працює так: пошук → структура → читання рядків. `search` знаходить сторінку та її символи,
`page` показує символи файлу з діапазонами рядків, і агент читає лише ці рядки своїм інструментом
для файлів. `callers` відповідає на «що зламається, якщо це змінити». Отримавши план,
специфікацію чи журнал, агент передає їхні шляхи в параметр `docs`
інструмента `search` і отримує діапазон рядків кроку за його міткою (`T5k`) або словами назви
(`wiki search T5k --docs plan.md` у командному рядку). Кожен шлях друкується один раз, далі
`  start-end  label` на збіг; `load-profile` і `load profile` збігаються однаково, але після точних
збігів. Якщо `limit` відсікає мітку, що повторюється в одному документі з тим самим початком
(`N11: …` у журналі), видно і її перший, і останній запис. План, специфікацію й журнал варто
передавати разом: ID часто є міткою лише в одному з них. Порожній запит видає перші 200 міток
(більше — через `limit`, останній рядок каже, скільки відсічено). Текст документа не шукається, для
нього лишається grep.
Якщо жодна мітка не містить слова поспіль, запит, що називає кілька міток одну за одною
(`Global constraints Per-batch procedure Pins`, `T9a T9k Rows`), повертає кожну в порядку запиту:
частина з двох і більше слів або з ID на початку відкриває свою мітку, одне звичайне слово має бути
всією міткою, а перший рядок називає слова, що не відкривають жодної. Інакше відповідають мітки, що
починаються з ID на початку запиту (`11.4`, `T3a`), інакше мітки з усіма словами запиту, крім службових, у будь-якому порядку;
а коли не відповіла жодна мітка — рядки таблиць, що містять слова запиту поспіль (`| W21 | D12 |` для `W21`
чи `D12`), спершу зі збігом у першій клітинці; перший рядок називає цей запасний пошук. Порожня відповідь каже, що мітки не знайдено, і радить інші слова або grep.

| агент | що записує `wiki setup` | що каже йому користуватися вікі |
|---|---|---|
| Claude Code | `.mcp.json` (repo) або `claude mcp add-json` (local) | інструкції сервера; інструменти завантажуються одразу |
| pi | `.pi/mcp.json`, кроки навігації в `.pi/APPEND_SYSTEM.md`, скіл `wiki-navigation` | кроки й скіл (інструкцій сервера pi не показує) |
| Cursor | `.cursor/mcp.json` | описи інструментів (у наших прогонах їх вистачило) |
| Codex | `.codex/config.toml`, [правила навігації](#правила-навігації) в `AGENTS.md` | `AGENTS.md` |
| будь-який інший MCP-клієнт | — ([вручну](#інші-mcp-клієнти)) | правила навігації в його файлі інструкцій |

#### `wiki setup`

`wiki setup` налаштовує агентів, щоб вони самі користувалися вікі. Запускайте в корені проєкту:

    wiki setup [--agent claude,pi,cursor,codex] [--scope repo|local] [--hook | --no-hook] [--memory | --no-memory] [--remove] [--yes]

Команда компілює `.` у `.nollm-wiki`, потім встановлює MCP-сервер (`wiki serve --source .`) і те, що
каже кожному агентові ним користуватися. pi отримує короткі кроки навігації в
`.pi/APPEND_SYSTEM.md`, який pi додає до свого системного промпту, і скіл `wiki-navigation` (як
шукати код і правила памʼяті). Claude Code не отримує скіла: інструкції сервера, де ті самі кроки навігації, він
показує й так, а сервер позначає свої інструменти для завантаження одразу, а не через `ToolSearch`;
власну памʼять Claude Code вікі читає сама. Codex не читає ні того, ні того, тож отримує правила
навігації в `AGENTS.md`, між маркерами `<!-- wiki:navigation -->`. Агенти визначаються автоматично
(`.claude/`, `CLAUDE.md` чи `claude` у `PATH`; `.pi/` чи `pi` у `PATH`; тека `.cursor/` чи `.codex/`,
але не `.codex/`, що є власною текою Codex), якщо `--agent` їх не називає. Коли жодного агента
не знайдено і `--agent` не задано, setup у терміналі питає, кого
налаштувати (номери чи назви, порожній рядок — нікого); без термінала, або коли нікого не вибрано,
він однаково компілює вікі, пише рядки в ignore-файли й теку памʼяті, не налаштовує жодного агента,
пише в stderr `no agent set up: the wiki is in .nollm-wiki/; run wiki setup --agent … later` і
виходить з кодом 0. `--remove`, коли агента не знайдено і `--agent` не задано, нічого агентського не прибирає: пише в
stderr `no agent found: nothing agent-specific removed; pass --agent … to remove one agent's wiring`
і виходить з кодом 0.

- `--scope repo` — закомічені файли для всієї команди: `.mcp.json`, `.pi/mcp.json`,
  `.pi/APPEND_SYSTEM.md`, `.cursor/mcp.json`, `.codex/config.toml`, `AGENTS.md`,
  `.agents/skills/wiki-navigation/SKILL.md` і `.nollm-wiki/` у `.gitignore`. Для файлу, який setup
  записав, а git ігнорує, він друкує `warning: <file> is ignored by git; teammates will not get it`.
- `--scope local` — лише ця робоча копія: сервер для Claude Code додається через
  `claude mcp add-json wiki … --scope local`, інші файли записуються, а ті, що setup створив,
  вносяться в `.git/info/exclude`, зокрема `/.agents/memory/`, коли памʼять увімкнена; уже наявний
  `.codex/config.toml` редагується й туди не вноситься. Файл, який git уже відстежує,
  пропускається; для нього беріть `--scope repo`.
- Памʼять агента ввімкнена за замовчуванням: обидва варіанти створюють `.agents/memory/`.
  З `--no-memory` тека `.agents/memory/` не створюється, компіляція йде без памʼяті, а сервер
  реєструється як `wiki serve --source . --memory none`. Повторний запуск з іншим вибором
  перемикає зареєстрований сервер; сервер, доданий через CLI `claude`, або таблиця `wiki` у
  `.codex/config.toml` з вашими власними налаштуваннями лишаються як є, і setup про це повідомляє:
  видаліть такий запис і запустіть setup знову.
- Обидва варіанти записують сервер Codex у власний `.codex/config.toml` проєкту, і CLI `codex` для
  цього не потрібен; див. [Codex](#codex).
- Без `--scope` setup питає в терміналі, а без термінала завершується з помилкою. Setup питає лише
  тоді, коли і stdin, і stdout — термінали; `--yes` — те саме, що відсутність термінала.
- Хук запиту (`--hook`, за замовчуванням вимкнений) додає рядки коду з вікі до кожного запиту,
  перш ніж його побачить модель. Claude Code отримує запис `UserPromptSubmit`
  (`wiki hint --claude-hook`) у `.claude/settings.json` (`settings.local.json` з `--scope local`);
  pi — `.pi/extensions/wiki-hint/index.ts`. Хук мовчить, коли вікі немає, її не прочитати або
  нічого не збіглося, і ніколи не блокує запит. За замовчуванням він вимкнений, бо досі спрацьовує
  приблизно на третині розмовних запитів (див. `docs/KNOWN_GAPS.md`). Запуск без `--hook`
  (`--no-hook` — те саме) прибирає хук, який записав попередній setup, розпізнаючи його так само
  точно, як `--remove`, і друкує `removed <file> …: the prompt hint is off by default now; run setup
  again with --hook to keep it`; файл, який setup не може прочитати, лишається як є з рядком
  `left <file> as it is: …`, і запуск не падає. Щоб лишити хук, запустіть setup з `--hook` знову: setup цей вибір
  не запамʼятовує. Запуск лише для частини агентів (`--agent claude`) не чіпає хук решти.
- `--remove` видаляє рівно те, що записав setup, разом із хуками, а блок Codex — лише якщо це
  точнісінько той, що записав setup (разом із ним іде й файл, якщо в ньому більше нічого не
  лишилося, а потім і `.codex/`). Рядки в ignore-файлах, `.nollm-wiki/` і нотатки памʼяті лишаються.

У проєкті з `CLAUDE.md` і без `AGENTS.md` `--agent codex` додає сервер Codex, але пропускає правила
навігації (код виходу 1) і не створює `AGENTS.md`: коли є обидва файли, pi читає лише `AGENTS.md`,
тож перестав би бачити `CLAUDE.md`. `AGENTS.md`, який там створив попередній запуск setup і в якому
немає нічого, крім правил, з тієї ж причини видаляється. Щоб отримати правила, перейменуйте `CLAUDE.md` на `AGENTS.md`,
створіть новий `CLAUDE.md` з одним рядком `@AGENTS.md`, щоб Claude Code і далі його читав, і
запустіть setup знову; тоді Codex і Cursor читатимуть ті самі правила. Якщо `CLAUDE.md` закомічений,
це змінює спільні файли команди: запускайте setup з `--scope repo`, бо локальний варіант пропускає
відстежуваний `AGENTS.md`.

Кроки для pi записуються позначеним блоком (`<!-- wiki:navigation -->`) у `.pi/APPEND_SYSTEM.md`;
`--remove` прибирає блок, а файл — коли в ньому більше нічого не лишилося. pi бере
`.pi/APPEND_SYSTEM.md` проєкту замість файлу зі своєї теки агента (`$PI_CODING_AGENT_DIR`, інакше
`~/.pi/agent`), ніколи обидва. Тож коли в теці агента є `APPEND_SYSTEM.md`, а в проєкті немає,
setup пропускає кроки (код виходу 1), щоб не сховати ваш файл у цьому проєкті; скопіюйте його в
`.pi/APPEND_SYSTEM.md` і запустіть setup знову, щоб мати обидва. Коли `AGENTS.md` у теці агента
містить блок `<!-- wiki:navigation -->` — старішу копію, покладену вручну, яку pi завантажує в
кожному проєкті, — setup попереджає; теку агента він ніколи не редагує.

`wiki`, встановлений nollm-wiki (запущений як `~/.nollm-wiki-home/bin/wiki` або з `$NOLLM_WIKI_HOME/bin`),
агенти запускають як `"${NOLLM_WIKI_HOME:-$HOME/.nollm-wiki-home}/bin/wiki"` через `sh -c` (хук промпту
виконує цей рядок, розширення pi саме будує той самий шлях), тож жодному агентові не треба мати його
в `PATH`, і нічий домашній шлях не потрапляє в спільний файл; з `NOLLM_WIKI_HOME`, відмінним від
`~/.nollm-wiki-home`, setup попереджає, що агентам потрібна і ця змінна (домашній шлях із `"`, `$`,
зворотним апострофом чи `\` цей рядок не підтримує). Запис в обох формах setup вважає своїм і
переписує у форму, яку пише цей `wiki`. Будь-який інший `wiki` (зібраний з коду, встановлений
деінде) кожен агент запускає просто як `wiki`, тож `wiki` має бути в `PATH`; setup попереджає, якщо
його там немає або перший `wiki` у `PATH` — інша програма (її `--version` не друкує `wiki <версія>`
протягом 2 секунд): агенти запустять саме її, тож поставте цей `wiki` у `PATH` раніше. Запускати
двічі безпечно. Запис, файл чи блок на тому самому місці з іншим вмістом лишається як є, і setup про
нього повідомляє, робить решту й виходить з кодом 1. JSON-конфіг, який редагує setup, переписується
з відступом у 2 пробіли, ключі та їхній порядок зберігаються.

Після setup: pi завантажує файли проєкту лише після того, як ви довірите проєкт (`/trust` або
`--approve` у режимі print), а `cursor-agent` завантажує новий сервер лише після того, як його
ввімкнено (`cursor-agent mcp enable wiki`); редактор Cursor показує його в Settings → Tools & MCP.

#### Claude Code вручну

    claude mcp add-json wiki '{"command":"wiki","args":["serve","--source","."]}' --scope local

або запис `mcpServers` з розділу [MCP-сервер](#mcp-сервер) у `.mcp.json` проєкту. Claude Code
показує інструкції сервера з кроками навігації, тож для пошуку коду скіл не потрібен; вікі читає
власну памʼять Claude Code, див. [Памʼять агента](#памʼять-агента).

#### pi

`wiki setup --agent pi` записує `.pi/mcp.json`, кроки навігації в `.pi/APPEND_SYSTEM.md` і скіл
`wiki-navigation`; pi завантажує їх після `/trust` (`--approve` з `pi -p`). Без скілу pi не обійдеться: інструкцій MCP-сервера для
серверів `direct` він не показує, тож про вікі знає лише з описів інструментів і скілу. Без нього в
наших прогонах модель шукала через grep, а коли встановлене користувачем розширення змушувало pi
завантажити скіл перед відповіддю (у нас це було skill-first), вона брала невідповідний
(`systematic-debugging` на питаннях «де знаходиться…»).

Вручну — `.pi/mcp.json` у проєкті:

```json
{ "mcpServers": { "wiki": { "command":"wiki", "args": ["serve", "--source", "."], "exposure": "direct" } } }
```

і [правила навігації](#правила-навігації) в `.agents/skills/wiki-navigation/SKILL.md`, під front
matter з `name: wiki-navigation` і `description:`, що каже, коли скіл потрібен (`wiki setup`
пише «Find where something is or how it works in this project's code. Use before grep, find or
reading whole files, whenever the task needs a function, type, handler or module location.»); за
ними pi скіл і знаходить.

Залиште лише сервер проєкту: якщо в `~/.pi/agent/mcp.json` теж є сервер вікі, під будь-якою назвою,
видаліть його. З обома модель бачить кожен інструмент вікі двічі під двома назвами (pi називає їх
за сервером: `mcp__wiki__search` для цього), а скіл, який пише `wiki setup`, називає лише
`mcp__wiki__*`. Щоб перевірити, не даючи pi змінювати файли:
`pi -p --approve --no-session --exclude-tools edit,write "where is …"`.

Виміряно по одному разу на питання з Mellum2.1 12B-A2.5B на llama-server, на трьох питаннях про
приватний проєкт з розділу [Виміряне](#виміряне): усі шість відповідей правильні; зі скілом три
питання забрали 10 викликів інструментів і 109 с, без нього 19 і 160 с. Зі скілом pi відповідав на
«що викликає X» через `search`, потім `callers`, і в цих прогонах не завантажував невідповідного
скілу. Питання, чиї слова відрізняються від слів у коді (`credentials` для `load_member_creds`), все
одно закінчилося grep.

#### Cursor

`.cursor/mcp.json` у проєкті (або `~/.cursor/mcp.json` для всіх проєктів) приймає той самий запис:

```json
{ "mcpServers": { "wiki": { "command":"wiki", "args": ["serve", "--source", "."] } } }
```

Cursor запускає сервер у теці проєкту, тож `--source .` працює. У `cursor-agent` новий сервер
вимкнений, доки ви його не схвалите, а `cursor-agent` скидає це схвалення щоразу, коли змінюється
команда в записі; тоді сервер мовчки не завантажується. У наших прогонах агент викликав `search` і
`callers` без додаткових інструкцій.

`cursor-agent -p` (неінтерактивний режим) відхиляє кожен виклик MCP-інструмента, якщо не запущений з
`--force`; `--mode ask --force` дозволяє інструменти вікі й однаково не дозволяє редагувати файли.
Перевірено з `cursor-agent` 2026.10.22. У редакторі Cursor (3.30) з відкритою текою проєкту сервер
із `.cursor/mcp.json` проєкту зʼявився в Settings → Tools & MCP і запрацював після перезавантаження
вікна, також коли git ігнорує файл (local scope).

#### Codex

`wiki setup --agent codex` дописує це у власний `.codex/config.toml` проєкту й створює файл, якщо
його немає; з `--no-memory` у `args` додатково є `"--memory", "none"`:

```toml
[mcp_servers.wiki]
command = "wiki"
args = ["serve", "--source", "."]
```

Тоді сервер існує лише в цьому проєкті, за будь-якого `--scope`: Codex запускає його там, де
запускали setup, а не в кожній сесії. Codex читає `.codex/config.toml` проєкту лише в проєкті, якому
довіряє, тому setup завершується рядком `Codex loads the server only in a project it trusts: run
codex in the project and accept the question, or add [projects."<project path>"] trust_level =
"trusted" to ~/.codex/config.toml`, де `<project path>` замінено абсолютним шляхом проєкту.
Команда `codex` сама ставить питання про довіру; настільний застосунок Codex (застосунок ChatGPT)
при відкритті проєкту не питав і завантажив сервер проєкту, щойно цей запис зʼявився в
`~/.codex/config.toml`. Сам setup ніколи не редагує власний `~/.codex/config.toml` Codex і не
вважає ознакою проєкту теку `.codex/`, якщо це і є власна тека Codex. Перевірено з
codex-cli 0.169.0-alpha.11.1 (версія, вбудована в цей застосунок); яка раніша версія першою читає
файл проєкту, не перевірено.

Setup дописує блок лише там, де може його впізнати. Блок його власний, коли за заголовком
`[mcp_servers.wiki]` ідуть рівно рядок `command` і один із двох рядків `args`; тоді setup
перемикає памʼять, переписуючи лише `args`, а `--remove` його видаляє. Усе інше, що може визначати
сервер (додаткові ключі на кшталт `env` чи `cwd`, ключ у лапках чи з крапками, вбудований
`mcp_servers = { … }`, файл, до якого веде посилання, або такий, що його в local-режимі відстежує
git), лишається як є, і setup повідомляє про це рядком `skipped .codex/config.toml wiki server: …`
(код виходу 1), бо друге визначення зробило б файл некоректним; тоді додайте сервер вручну. Інші
таблиці у файлі ніколи не змінюються.

Коли `codex` є в `PATH`, кожен запуск setup і `--remove`, що може редагувати файл проєкту, питає
Codex про сервер `wiki` на всю машину (`codex mcp get wiki`, поза будь-яким проєктом, щоб не
відповів файл батьківського проєкту). Такий сервер — інший сервер, і він далі працює в кожній іншій
сесії Codex: setup повідомляє про нього й називає команду, що його видаляє, під час запуску, який
застає проєкт без власного сервера `wiki` (код виходу 1); `--remove` згадує про нього під час
кожного запуску, не змінюючи коду виходу. Без `codex` у `PATH` setup туди не дивиться.

Інструменти вікі позначені як «лише читання», тож Codex запускає їх без запитів, зокрема в
`codex exec`. Але сам по них не тягнеться: йому потрібні [правила навігації](#правила-навігації) в
`AGENTS.md` проєкту. На трьох питаннях про цей репозиторій (codex-cli 0.164.0, пісочниця лише для
читання) без них він не викликав вікі жодного разу й один раз назвав не того викликача; з ними він
користувався `search`, `page` і `callers` і правильно відповів на всі три.

#### Інші MCP-клієнти

Додайте запис `mcpServers` з розділу [MCP-сервер](#mcp-сервер) у конфіг клієнта. Клієнтові, який
стартує не в теці проєкту, як Claude Desktop, потрібен абсолютний шлях до проєкту в `--source`.
Правила навігації покладіть у його файл інструкцій.

#### Правила навігації

Те, що `wiki setup` кладе в `AGENTS.md` для Codex, — для будь-якого агента, якому вони потрібні у
файлі інструкцій. Англійською, бо їх читає агент:

```
## Find code with the project wiki

1. Call the wiki `search` tool with the words of what you are looking for and `kind: "code"`.
   Each symbol line is `path:start-end  name  signature`.
2. Read only those lines with your file tool. The start and end lines are exact — do not
   re-derive them with grep.
3. Look up names you already know with `search`; put several in one query. Use `page` only to
   see every symbol of a module you have not seen. To see what calls a function, call `callers`
   with the path and `symbol` instead of grepping for its name.
4. Do not call grep, find or ls in the same turn as `search`. Wait for the `search` answer and
   read it first; most of the time it already holds what you need.
5. Pick the tool by the question: where something is defined or handled, `search`; who calls a
   function, `callers`; every occurrence of a literal string (an env var, a message, a config key),
   grep.
6. Only if search finds nothing relevant, try other words, then fall back to grep.
```

### MCP-сервер

`wiki serve` віддає скомпільовану вікі MCP-клієнтам через stdio. `wiki setup` пише цю
конфігурацію за вас; вручну вона така:

```json
{
  "mcpServers": {
    "wiki": { "command":"wiki", "args": ["serve", "--source", "."] }
  }
}
```

`--source .` працює для клієнтів, що стартують у теці проєкту, як Claude Code і pi; для решти,
наприклад Claude Desktop, вкажіть абсолютний шлях до проєкту.

    wiki serve [--source <project>] [--dir <out>] [--tools <list>] [--memory <none|DIR>]

- `--source <project>` — ще й компілювати цей проєкт і тримати вікі в актуальному стані.
- `--dir <out>` (`<project>/.nollm-wiki` з `--source`, інакше `.nollm-wiki`, якщо така тека існує, інакше
  `out`) — скомпільована вікі, яку віддавати.
- `--tools <list>` (`search,page,callers`) — які інструменти відкрити, через кому, з
  `search`, `page`, `neighbors`, `callers`, `lint`.
- `--memory <none|DIR>` (можна повторювати) — з `--source`: `none` вимикає всю памʼять, і теки
  агентів, і `.agents/memory`, а `DIR` бере теки замість пошуку тек памʼяті агентів (`none` разом
  із `DIR` — помилка використання); `DIR`, якої
  немає на момент старту, підхоплюється, коли зʼявиться, якщо існує її батьківська тека (її відстежують рекурсивно; без
  батьківської теки потрібен перезапуск). На Linux відстеження батьківської теки коштує один watch
  inotify на кожну теку під нею, тож для великої батьківської теки передайте наявну теку. `.agents/memory` компілюється, якщо не
  передано `--memory none`. Зміна поведінки: до 0.6.6 `none` вимикав лише пошук тек, а
  `.agents/memory` компілювалася й далі.

| Інструмент | Параметри | Повертає |
|---|---|---|
| `search` | `query` (порожній разом із `tag` дає список сторінок з тегом), `tag?`, `kind?` (`code` без тестових сторінок, `tests`, `docs`, `text`, `markdown`, `code:<lang>`), `docs?` (шляхи markdown відносно `--source`, інакше робочої теки сервера; шукає за заголовками й жирними кроками, а коли жодна мітка не збіглася — за рядками таблиць, не разом із `kind` чи `tag`), `limit?` (5 із запитом, 10 з `docs`; без обмеження для списку за тегом), `format?` (`lines` за замовчуванням або `json`) | Текст `lines`, описаний у [search](#search), або `[{id, title, summary, updated, score, snippet, path, symbols}]` з `json` |
| `page` | `id` (ідентифікатор, назва чи шлях), `full?` (false), `max_tokens?` (4000 для структури) | Структура або вся сторінка; сторінка нотатки памʼяті — це її текст |
| `neighbors` (з `--tools`) | `id`, `depth?` (1; із `symbol` — без обмеження), `max_tokens?` (4000), `max_nodes?`, `full?`, `kind?`, `symbol?` | Пакет контексту, або з `symbol` — функції, які викликає ця функція |
| `callers` | `id`, `symbol`, `depth?` (1), `max_tokens?` (4000) | Функції, що викликають `symbol`, з рядками кожного виклику |
| `lint` (з `--tools`) | — | JSON `{total_pages, broken_links, orphans, large}` |

`tag` і `format` у `search`, `full` у `page` та `max_tokens` у `callers` сервер приймає, але в схемах
інструментів їх немає: агенти їх не передавали, а кожне поле схеми коштує токенів у кожному запиті.
Результат `page` чи `callers`, обрізаний бюджетом, сам називає `max_tokens`.

Інструменти повторюють CLI, але з меншими значеннями за замовчуванням: `max_tokens` — 4000 там, де
CLI не обмежує, а `search` повертає 5 результатів замість 10, бо кожен рядок результату агент
перечитує на кожному наступному ході. `lint` відкривається лише тоді, коли його названо в
`--tools`: він потрібен тому, хто доглядає вікі, а кожен відкритий інструмент коштує токенів схеми
в кожному запиті. `neighbors` теж вмикається лише явно: агенти майже ніколи його не викликали (16 з
11 056 викликів у вимірюваннях, 0 з 37 на тестовій машині), а його схема займала близько чверті
токенів інструментів на кожному ході. `--tools search,page,neighbors,callers` повертає його. Закомічений
блок AGENTS.md чи skill, що його ще називає, `wiki setup` не оновлює: блок, який відрізняється від
його власного, він лишає як є й повідомляє про це; видаліть блок або файл skill і запустіть setup ще раз.

**Актуальність.** З `--source` сервер компілює проєкт сам. Наявну вікі він віддає одразу, а
компіляція йде у фоні; виклик чекає цю першу компіляцію щонайбільше 1 с. Якщо вікі немає, перша
компіляція йде до старту, і помилка завершує сервер. Далі він стежить за проєктом і інкрементально перекомпільовує після правок (ігноровані шляхи на
кшталт `target/`, тек збірки та `.git` цього не запускають). Кожен виклик інструмента чекає до 5 с,
поки скомпілюються правки, зроблені до нього. Якщо перекомпіляція впала або ще йде, сервер віддає
останній вдалий знімок, а до результатів додається рядок `wiki may be stale: <reason>`. Короткочасні
файли-барʼєри, по одному на виклик, лежать у `<dir>/.serve/`. Кілька серверів на одному `<dir>` (по
одному на сесію агента) ділять його: компілює той, що тримає `<dir>/.serve/writer.lock`, інші
відповідають з того, що він записав, і один з них перебирає її на себе, коли він завершується. Без `--source` сервер лише читає
вікі: перед кожним запитом він звіряє відбиток `index.json` і перечитує вікі після перекомпіляції;
якщо перечитати не вдалося, лишається попередній знімок, а спроба повторюється на наступному запиті.

**Замінений бінарник.** Сервер, який бачить, що його виконуваний файл `wiki` замінили чи видалили
(нове встановлення, перезбірка, симлінк на іншу збірку), до кінця життя перестає компілювати й писати
в `<dir>`, щоб старий компілятор не переписав новішу вікі. Він не завершується і далі відповідає з
`<dir>`, перечитуючи її, як описано вище. Про це один раз сказано в stderr, а кожен результат отримує
рядок `wiki may be stale: the wiki server is out of date, ...`: перезапустіть сесію агента або
перепідключіть MCP-сервер.

### Памʼять агента

Агенти тримають нотатки як Markdown-файли. Вікі компілює теки, у які вони пишуть, а `search` і
`wiki hint` показують відповідні нотатки після коду. Джерела:

- **`.agents/memory/`** у проєкті. `wiki setup` створює її в обох режимах, якщо не передано `--no-memory`; з `--scope local` ще й
  вносить `/.agents/memory/` у `.git/info/exclude`, тож нотатки лишаються приватними. `wiki compile`
  включає її, якщо не передано `--memory none`.
- **Власні теки агентів.** Їх шукають `serve --source` і `wiki setup`. Поки що це
  `<config dir>/projects/<slug>/memory/` Claude Code, де config dir — це `CLAUDE_CONFIG_DIR` або
  `~/.claude`, а `<slug>` — шлях основної робочої копії репозиторію, у якому кожну одиницю UTF-16, що
  не є ASCII-літерою чи цифрою, замінено на `-` (тож кирилична чи акцентована літера дає один `-`, а
  символ поза BMP — два), довше за 200 одиниць обрізається з хешем, як у Claude Code.
  Тож worktree чи підтека ділять теку своєї основної копії. Тека `logs/` усередині пропускається,
  як і `MEMORY.md`.
- **`--memory DIR`** (можна повторювати) для будь-якої іншої теки. У `serve` `--memory DIR` бере
  теки замість пошуку. У `compile` і `serve` `--memory none` вимикає всю памʼять, зокрема
  `.agents/memory` (зміна поведінки: раніше `.agents/memory` лишалася).

Звичайний `wiki compile . out` компілює лише `.agents/memory` і теки з `--memory`, але ніколи теки
агентів, тож опублікований сайт ніколи не несе приватних нотаток. Тому звичайний
`wiki compile . .nollm-wiki` прибирає нотатки агентів з `.nollm-wiki` до наступної перекомпіляції сервером, а
`wiki hint` читає саме `.nollm-wiki`.

Міграція: `compile --memory local` більше не існує, а нотатки з теки користувача попередніх
випусків більше не компілюються. Перенесіть їх у `.agents/memory` або передайте
`--memory <та тека>`.

`search` показує код і документи так, ніби нотаток немає, а потім до двох нотаток, по одній на
рядок, як `memory (<origin>): <path> — <summary>`, за яким, коли збігся її текст, іде уривок в
окремому рядку з відступом. Нотатка показується, коли слово запиту з чотирьох чи більше символів є в
її назві, псевдонімах чи описі, або запит називає день її `updated`, або вона набирає щонайменше
вдвічі більше за найкращий збіг у коді (нотатка оцінюється за сторінками проєкту разом із нотатками,
збіг у коді — лише за сторінками проєкту). Нотатки проходять фільтри `code` і `docs`, а
`wiki hint` додає один рядок памʼяті за тим самим правилом (див. [hint](#hint)). Нотатки ніколи не
зсувають ранг сторінки коду: PageRank і медіана для `llms.txt` рахуються лише за сторінками проєкту.

Кожен рядок нотатки каже, звідки вона: `memory (local): /abs/x.md — summary` для нотатки в теці
агента, у теці `--memory` чи у файлі `.agents/memory`, якого git не відстежує (або git немає), і
`memory (repo, Jane Doe): .agents/memory/x.md — summary` для закоміченої, з іменем автора останнього
коміту, що змінив файл (ніколи не email; без імені, коли git не може його назвати), `, you`, коли
email автора того коміту збігається з вашим `git config user.email` без огляду на регістр
(`memory (repo, Jane Doe, you): …`; без git чи без email ніхто не «ви»; email лише порівнюється,
його ніде не зберігають і не показують), і `, edited`, коли робоча копія відрізняється від того
коміту. У JSON збіги мають `"memory": true`, `"origin": "local"` чи `"repo"`, `"author"`, коли він
відомий, `"mine": true` для ваших нотаток і `"edited": true`, коли файл змінено. Походження
визначається під час компіляції — `wiki compile` і кожної перекомпіляції `serve --source`; відповідь
на `search` чи хук git не викликає. Нотатки впорядковано за довірою, а серед рівних зберігається
порядок за оцінкою: спершу локальні, далі ваші власні чи змінені закомічені, далі решта; `search`
показує дві найдовіреніші нотатки, що пройшли відбір, а рядок памʼяті в хуку — найдовіренішу.

Дата в запиті знаходить нотатки памʼяті за той день: `12 жовтня`, `October 12`, `12.10`,
`2026-10-12` (українські, російські та англійські назви місяців; `DD.MM` потребує двох цифр дня і
місяця; без року підходить будь-який рік). Сторінки проєкту за датою не знаходяться ніколи.

Нотатка може замінити старішу через `supersedes:` у front matter (назви, псевдоніми чи
ідентифікатори, у синтаксисі `aliases:`). Тоді старіша нотатка ніколи не зʼявляється після рядків коду, а `wiki hint` її не показує; список за тегом
дописує ` (superseded by <id>)` після її рядка (`"superseded_by"` у JSON).
Зіставляються лише нотатки памʼяті, імʼя, що ні з чим не збіглося, ігнорується, а коли таких нотаток
кілька, показується найменший ідентифікатор.
Закомічена нотатка ніколи не замінює незакомічену.

Front matter будь-якої Markdown-сторінки: `title:` — це назва (інакше перший `# заголовок`, інакше
назва файлу), а `description:` — однорядковий опис, який друкують рядки памʼяті і за яким збігається
поріг; `aliases:` і `tags:` пишуться як `a, b`, `[a, b]` або
YAML-список; теги переводяться в нижній регістр, `#` відкидається. Дата сторінки береться з
`updated`, `modified` чи `date`, потім з тих самих ключів у блоці `metadata:` на один рівень
глибше, потім з назви файлу, що починається з `YYYY-MM-DD`. Інша граматична форма слова теж дає
збіг (`provisioning` знаходить `brew_provision`, `сторінок` знаходить `Сторінка`): слова запиту й
полів порівнюються за основою Snowball, англійською чи українською за письмом, нижче за точний і
префіксний збіг у ранжуванні. Текстову сторінку понад приблизно 16 000 символів (4000 токенів)
`wiki lint` позначає як `large` (див. [lint](#lint)).

Ці правила містить скіл pi (`<memory-dir>` — це `.agents/memory`); якщо в агента скілів немає,
скопіюйте їх у його файл інструкцій. Правила англійською, бо їх читає агент:

```
Notes about this project live in `<memory-dir>`; `search` lists up to two of them after the code
hits, each on a `memory (<origin>):` line, and the prompt hook, when `wiki setup --hook` added it,
adds one.

- Write one note per fact or topic, named for what it says.
- A note not written in English needs English `aliases:` in its front matter
  (search words are English).
- A journal note is named `YYYY-MM-DD.md` and has the date in its H1.
- Search first; update the note that exists instead of adding a copy.
- When a decision changes, update its note. If you write a new note instead, add `supersedes: <old note's title>` to it.
```

### CLI

    wiki [--jobs N] <command>

| команда | що робить |
|---|---|
| `compile` | компілює проєкт у вікі |
| `search` | сторінки й символи за запитом |
| `page` | структура файлу: по рядку на символ з діапазоном рядків |
| `callers` | функції, що викликають функцію |
| `neighbors` | пакет контексту навколо сторінки в межах бюджету, або з `--symbol` — що викликає функція |
| `lint` | биті посилання, сторінки-сироти, сторінки, завеликі для пакета |
| `serve` | MCP-сервер — див. [MCP-сервер](#mcp-сервер) |
| `hint` | рядки коду для тексту задачі, для хуків запиту |
| `setup` | встановлює сервер для Claude Code, pi, Cursor і Codex — див. [Агенти](#агенти) |
| `generate` | синтетичний корпус для демо й звітів про помилки |

`--jobs N` задає кількість потоків для `compile` (за замовчуванням як у Rayon, зазвичай за числом
ядер); результат від цього не залежить. Команди-запити читають `--dir <out>` (за замовчуванням
`.nollm-wiki`, якщо така тека існує, інакше `out`) і ніколи не перекомпільовують.

#### compile

    wiki compile [OPTIONS] <INPUT> <OUTPUT>

- `--incremental` — брати відбитки рендерингу з `<OUTPUT>/.wiki/cache.json` і пропускати незмінені сторінки.
- `--no-ignore` — не застосовувати правила `.gitignore`/`.ignore`/прихованих файлів під час обходу
  `<INPUT>` і обходити також теки процесу та сторонній код.

Без `--no-ignore` тека з назвою `superpowers` (на будь-якій глибині) і сторонній код (`third_party`,
`third-party`, `vendor`, `vendored`, `node_modules`) не обходяться: висновки цих артефактів процесу
несуть нотатки памʼяті, а чужий код витісняє код самого проєкту. Після запуску `compile` друкує,
скільки файлів пропущено, наприклад `Skipped: superpowers 2280, third_party 97, ignored 16800`: по
одному числу на назву теки та `ignored` для правил `.gitignore`/`.ignore`/прихованих файлів. Файл
рахується один раз, за найзовнішньою пропущеною текою; `.git`, `<OUTPUT>` і теки памʼяті не
рахуються, а з `--no-ignore` такого рядка немає.
- `--emit-json` — ще й записати `graph.json` (граф вузлів і ребер).
- `--project <NAME>` (за замовчуванням останній компонент вхідного шляху; `wiki`, коли його немає,
  як для `.`) — назва проєкту в `index.json`, `llms.txt` і `AGENTS.md`. Без нього `compile .` дає
  назву `wiki`, а `compile "$PWD"` — назву теки.
- `--memory <none|DIR>` (можна повторювати) — ще й компілювати теку памʼяті агента як позначені
  сторінки памʼяті. `<INPUT>/.agents/memory` компілюється теж; `--memory none` вимикає всю памʼять,
  зокрема цю теку (`none` разом із `DIR` — помилка використання); `--memory local` — помилка.
- `WIKI_TIMINGS=1` (змінна середовища) — друкувати в stderr по одному рядку `timings:` на кожну
  компіляцію: загальний час і мілісекунди за етапами, прочитані файли, записані сторінки.
  `wiki serve --source` і `wiki setup` його теж враховують; на вивід він не впливає.

Якщо в `<OUTPUT>` ще лежать сторінки, записані за старою схемою ідентифікаторів (давніша версія або
перейменовані відтоді джерела), `compile` попереджає в stderr і лишає їх на місці: видаліть їх або
компілюйте в чисту теку.

#### search

    wiki search [--kind K] [--tag T] [--docs FILE]... [--limit N] [--format lines|json] [--dir DIR] [QUERY]

- `--kind <k>` — `code` (усі `code:<lang>`, крім тестових сторінок), `tests` (лише тестові сторінки),
  `docs` (`markdown` і `text`) або один точний тип: `text`, `markdown`, `code:<lang>` (наприклад,
  `code:rust`; тестові сторінки відкинуто, як і для `code`). Нотатки памʼяті проходять і `code`, і
  `docs`, але ніколи `tests`; до двох, що проходять поріг, йдуть після збігів рядками `memory (<origin>):` з уривком (див.
  [Памʼять агента](#памʼять-агента)). Тестова сторінка — файл коду в теці `tests` або з назвою
  `test_*`, `*_test.*` чи `*_tests.*`; інші розкладки (тека `test`, файли `*.test.*` і `*.spec.*`,
  модуль Rust `tests.rs`, вбудований код `#[cfg(test)]`) лишаються в `code`. `code` і `tests`
  розділяють збіги вже після підрахунку балів, тож сторінка має той самий бал, що й у пошуку без розділу.
  Коли тестова сторінка була б першою сторінкою пошуку `code`, останній рядок каже
  `tests also match; use kind "tests"` (але не після рядка `in test pages only`).
- `--tag <tag>` — лише сторінки з цим тегом (`#` і регістр не враховуються; `a` збігається і з `a/b`). Без
  запиту дає список усіх таких сторінок. Потрібен запит, `--tag` або `--docs`.
- `--docs <FILE>` (можна повторювати) — шукати за заголовками й жирними кроками цих файлів Markdown замість
  вікі (див. [Агенти](#агенти)); шляхи відносно поточної теки, скомпільована вікі не потрібна, а
  `--kind`, `--tag` і `--dir` з ним не поєднуються (помилка використання).
- `--limit <N>` (`10` із запитом) — максимальна кількість результатів.

За замовчуванням — по рядку на сторінку: `id  path  [date  ]title — summary`. Під сторінкою коду до
3 рядків з відступом називають символи, що збіглися: `  path:start-end  name  signature  — doc`
(нумерація з 1, межі включно; для методів `name` має вигляд `Owner::name`). Елемент збігається за
повною назвою або за одним зі слів, на які її ділять `_` і зміна регістру (`clampQoSLevel`: `clamp`,
`qo`, `s`, `level`); два сусідні слова, кожне не довше двох символів, збігаються ще й разом (`qos`).
Символ показується, коли
набирає щонайменше 30% від найкращого символу у відповіді або є найкращим на своїй сторінці, тож
сторінка з будь-яким збігом зберігає один, а тестовий код рахується з половинною вагою. Функція, назва
якої має рівно одне інше не тестове визначення в іншому файлі, отримує під собою рядок із відступом у
чотири пробіли, `    also defined: path:start-end  name` (не для заголовкових оголошень, поєднаних зі своїм
визначенням, не коли в назви більше копій, не в `--format json`). Сторінка без рядків символів
натомість отримує уривок тексту в рядку з відступом у чотири пробіли. Слово запиту з `_` чи `::` або з
великою літерою після першої (`_ack`, `Router::slice_cap_for`, `OrderBook`) — ідентифікатор: початкове
підкреслення враховується, а його визначення — це елементи з точно такою назвою й тим самим регістром
(`max_weekly_fee_usd` не те саме, що `MAX_WEEKLY_FEE_USD`). Запит лише з ідентифікаторів перелічує
визначення кожного (до 3 і `--limit`) і більше нічого, хоч би скільки їх було в одному файлі; назва, що
є назвою модуля файлу в будь-якому регістрі (`auto_refill` для `auto_refill.rs`, тека для `mod.rs`),
спершу показує цей файл рядком сторінки. Першим рядком
`no symbol named <name>` йдуть назви, яких ніщо не визначає і які не є назвою файлу. Коли жодну
назву запиту не визначено, далі йдуть ранжовані сторінки, а рядок закінчується
`; the pages below match its words` (`their words` для кількох назв): вони збігаються зі словами
назви, а не з нею самою. З `code` назва, яку
визначено лише на тестових сторінках або яка є назвою модуля лише тестового файлу, натомість отримує
першим рядок `<name>: in test pages only; use kind "tests"`, а за ним самі ці тестові визначення
(рядки, які дав би `tests`) без ранжованих сторінок для неї. Відповідь для решти назв іде далі,
наче лише вони були в запиті. У такому запиті рядок функції чи методу закінчується сигнатурою з
`` [called by N: `callers`] ``, де N — скільки функцій перелічить `callers` (з визначенням
C++-оголошення), а коли N дорівнює 0, примітки немає. В іншому запиті визначення, яке ранжування
пропустило, додається після рядків своєї сторінки або сторінкою після збігів; порядок не змінюється.
Python-функція, визначена в тілі іншої функції, — символ лише для `search`: ні рядка `page`, ні
експорту, ні рядка в hint, ні ребра викликів (її виклики належать охоплювальній функції). Опис,
уривок чи doc довші за 160 символів обрізаються з `…`. `--format json` друкує
`[{id, title, summary, updated, score, snippet, path, symbols}]`, кожен символ —
`{path, start_line, end_line, name, signature, doc}`; нотатка памʼяті додає `memory`, `origin` і,
коли застосовно, `author`, `mine`, `edited`, `superseded_by`.

#### page

    wiki page [--full] [--max-tokens N] [--dir DIR] <ID>

`<ID>` — ідентифікатор сторінки або будь-що, що однозначно називає одну сторінку: її назва (у
будь-якому регістрі), slug назви, шлях до джерела чи унікальний кінець шляху (`query.rs`) або
абсолютний шлях усередині скомпільованої теки. Якщо нічого не збіглося, помилка перелічує найближчі
ідентифікатори (спершу сторінки не тестів) і, коли ім'я файлу без розширення (`thumbnail` для
`thumbnail.py`) є назвою елемента, до 3 місць, де його визначено (`defined in: app/images.py:1-3 thumbnail`,
`Owner::name` для члена класу), по одному на файл: спершу файли не тестів, типи й функції перед
значеннями, а поле C/C++ лише тоді, коли більше ніщо не має цієї назви. Шлях у теці, яку компіляція пропускає, чи в прихованій теці натомість дістає
примітку, що теку не скомпільовано, і для Markdown — пошук `docs`, яким його прочитати. `neighbors`
і `callers` розвʼязують `<ID>` так само.

```
$ wiki page calls.rs --dir .nollm-wiki
# Calls (calls)
  └ назва (id)
crates/wiki/src/calls.rs  code:rust
└ джерело          └ вид
Call edges between code items: matched by name at compile time (`resolve_calls`), followed…
imports:
  crate::formats::code::{module_stem, source_rank}
  …
15-20  fn  fn owner_key(owner: &str) -> &str  — The last segment of an owner, generics dropped…
38-50  type  struct Index<'a>  — What call sites resolve against: every function by name, every…
Index:
└ методи Index
  53-106  method  fn new(entities: &'a BTreeMap<String, Entity>) -> Self
  …
197-264  fn  pub fn resolve_calls(entities: &mut BTreeMap<String, Entity>, graph: &Graph)  — Fills…
└ рядки  └ вид, сигнатура                                                                  └ документація
```

Рядок елемента — `start-end  kind  signature`, далі `  → twin` для парного C++-оголошення чи
визначення і `  — doc`, коли є речення документації. Методи стоять під рядком `owner:`; тестові
елементи позначені `[test]`. Сторінка Markdown показує свої `headings:`, текстова — лише шапку.

Коли `--max-tokens` менший за структуру, частини відрізаються в такому порядку, поки не вміститься:
тестові елементи, потім документація, потім імпорти, потім елементи з кінця, а останній рядок каже,
що прибрано (`… dropped: 3 test items, 5 docs — pass max_tokens: 2412 for all`). З `--full` і
бюджетом, меншим за сторінку, сторінка коду друкує структуру в межах бюджету; будь-яка інша обрізається
по цілих рядках.

#### callers

    wiki callers [--depth N] [--max-tokens N] [--dir DIR] <ID> <SYMBOL>

Функції, що викликають функцію `<SYMBOL>` (`name` або `Owner::name`) на сторінці `<ID>`, по рядку
`start-end  kind  Owner::name` на кожну, згруповані за файлами; рядок закінчується на
`calls f at L1, L2` з рядками, де стоїть виклик, а тестовий код іде в кінці. `--depth 2` додає
викликачів викликачів; з `--max-tokens` першими відрізаються найдальші.

#### neighbors

    wiki neighbors [--depth N] [--max-tokens N] [--max-nodes N] [--full] [--kind K] [--symbol NAME] [--dir DIR] <ID>

Пакет контексту для агента в межах бюджету: обхід у ширину від `<ID>` на `--depth` кроків (1).
`--max-tokens` — жорстка межа оціненого розміру пакета (знаки/4), `--max-nodes` обмежує кількість
вузлів; сусіди беруться за центральністю (PageRank), а той, що не вміщується в залишок бюджету,
пропускається, і обхід іде далі. Ціль іде першою — сторінка коду як структура, — а сусіди за нею в
порядку центральності, найважливіші останніми, щоб найцінніший контекст стояв ближче до кінця. Без
`--full` першими до пакета потрапляють модулі, які ціль імпортує або які імпортують її, —
структурою, якщо вміщуються, — а решта одним рядком опису; далі всі вони друкуються в порядку
центральності, описаному вище.

`--symbol <NAME>` натомість друкує всі функції, які ця функція викликає, на всіх рівнях (або на
`--depth` з них), у форматі рядків `callers`.

#### lint

    wiki lint [--dir DIR]

Друкує кількість битих посилань, сторінок-сиріт і завеликих сторінок (понад 4000 токенів: таку
сторінку пакет `neighbors` за замовчуванням урізав би до опису; сторінки коду не перевіряються), а потім по
рядку на кожну. `[[посилання]]` в огороджених блоках, вбудованому коді та вихідному коді сторінки коду
не рахуються. Виходить з кодом 1, коли є бите посилання, тож `lint` може зупиняти збірку.

#### hint

    wiki hint [--dir .nollm-wiki] [--claude-hook] [TEXT]

Місця в коді для тексту задачі, як їх вставляє хук запиту: рядок-заголовок, далі до 8 рядків
`path:start-end  name  signature` (пробіли стиснуто до одного) з найкращих сторінок коду, не більше
2 на сторінку, без документації, тестів і рядка, діапазон якого містить інший рядок тієї ж сторінки;
сторінка без такого рядка дає `path  title`. Рядок із заголовка (`.h`, `.hh`, `.hpp`, `.hxx`) пропускається, коли раніший рядок не із заголовка
показує те саме повне імʼя. Рядок, чий власний текст (його рядки разом з коментарем над ним) збігається з найбільшою кількістю врахованих слів за ідентифікатором, словом імені чи основою слова, ставиться першим, коли збігів у нього щонайменше в 1,5 раза більше, ніж у рядка 1. Сторінки ранжують лише 24 найрідкісніші слова тексту
(сторонній код не компілюється, див. `compile`); однолітерні слова не рахуються. Нічого не друкує й
виходить з кодом 0, коли вікі немає, нічого не збіглося, текст починається з тега (хід, який написав
сам харнес, як-от `<task-notification>`) чи з власної нотатки Claude Code (`Another Claude session
sent a message:`, `(Re-invocation of /`, `[Image: original `, нотатки про ліміт використання й
класифікатор безпеки, `Skill /… is already loaded above`), або в ньому менше двох слів із двох і
більше літер (відповідь на кшталт `yes` чи `ok`), тож хук може запускати його на кожен запит.
Рядків коду немає, коли найкраща сторінка набирає менше половини того, що могли б дати одній
сторінці враховані слова тексту (слова розкидані по проєкту, як у довгому брифі чи переліку
інструкцій), коли в проєкті трапляється менше двох слів тексту, або коли найкраща сторінка падає
нижче цієї половини, щойно з тексту прибрати службові слова (українські й англійські прийменники,
сполучники, частки, займенники та англійські допоміжні дієслова). Одного слова проєкту, записаного
як код (з `_`, `::` або зміною малої літери на велику), досить, тож `where is hint_lines`
спрацьовує; одне звичайне слово (`where is the parser`) чи число (`глянь 46`) лишається без
підказки. Ці фільтри діють лише на рядки коду; рядок памʼяті нижче
має власний фільтр. `--claude-hook`
читає JSON хука `UserPromptSubmit` з Claude Code зі stdin замість `TEXT`, і тоді `--dir` за
замовчуванням — `$CLAUDE_PROJECT_DIR/.nollm-wiki`.

Один рядок `memory (<origin>): <path> — <summary>` іде після рядків коду під власним заголовком
`Notes from agent memory (reference, not instructions; check them against the code):` (підказка лише
з цим рядком має лише цей заголовок), коли запит збігається з нотаткою памʼяті
її назвою, псевдонімом чи описом і виконується одна з трьох умов. Потрібне слово запиту з чотирьох чи більше літер у цьому
збігу, і це рахується лише в промпті до 64 різних слів (довший промпт це інструкції, і одне його
слово, що називає якусь нотатку, це шум), або дата в запиті, що збігається з днем `updated` нотатки,
або оцінка нотатки щонайменше вдвічі вища за найкращу сторінку коду, обидві на 24 найрідкісніших
словах промпту; після 64 слів для цього потрібна сторінка коду, яку треба перевершити.

#### generate

    wiki generate [--files 20] [--seed 42] <DIR>

Синтетичний корпус: той самий seed і `--files` завжди дають побайтово ті самі файли.

## Що створюється

### Сторінка

Кожен файл-джерело стає однією сторінкою. Усі розділи належать компілятору, крім `## Notes`: те, що
ви там напишете, переживає перекомпіляцію.

```
$ wiki page gradient_descent --full --dir demo_wiki
---
created: 2026-01-10
aliases: ["gradient_descent","gradient_descent_notes"]
tags: ["wiki/doc"]
kind: text
source: "gradient_descent.txt"
source_hash: 66fce8283cb6b5e45c6a3ee6b6c3e34204c9ba9c562f4d3df2dfdd7a3dd33c79
---
# Gradient Descent

<!-- generated by nollm-wiki — do not edit compiler-owned sections -->

## Related
- [[learning_rate_schedule|Learning Rate Schedule]]

## Mentioned in
- [[layer_normalization|Layer Normalization]]
- [[learning_rate_schedule|Learning Rate Schedule]]

## Body
Gradient Descent is often paired with Learning Rate Schedule in production pipelines.

Revisit this after the next benchmark run.

## Notes
_(add your own notes here — preserved on recompile)_
```

Текст сторінки коду — це її вихідний код; символи з діапазонами рядків лежать в `items.json` і
показуються через `wiki page`.

### Файли

| Файл | Що це | Для кого |
|---|---|---|
| `<id>.md` | одна Markdown-сторінка з перехресними посиланнями на кожен файл-джерело | люди й агенти |
| `index.json` | каталог: записи, посилання, центральність | агенти й інструменти |
| `items.json` | елементи кожної сторінки коду з діапазонами рядків і викликами | агенти й інструменти |
| `index.md` | сторінка-покажчик | люди |
| `llms.txt` | стислий покажчик з описами в один рядок до 160 символів | моделі |
| `AGENTS.md` | як агентові користуватися цією вікі | агенти |
| `graph.json` | граф вузлів і ребер, лише з `--emit-json` | інструменти для графів |
| `.wiki/cache.json` (у теці виводу) | кеш інкрементальної компіляції | компілятор |

### Що читають агенти

- **`index.json`** — `{ project, root, entries: [...] }`, де `root` — імʼя самої скомпільованої
  теки. Кожен запис має `id`, `title`, `kind`, `aliases`, `tags`, `updated` (лише коли сторінка має
  дату), `path`, `page`, `summary` (`null`, коли опис вивести не вдалося), `degree_in`,
  `degree_out`, `pagerank`, `token_estimate`, `neighbors_out`, `neighbors_in`, `imports_out`,
  `imports_in` (ребра імпорту серед них), `defined` (імена визначень верхнього рівня) і `methods`.
  Запис нотатки памʼяті має ще `memory: true`, `origin` (`local` чи `repo`) і, коли застосовно,
  `author`, `mine`, `edited` і `superseded_by`.
- **`items.json`** — карта коду, винесена з `index.json`, щоб каталог лишався малим. Один обʼєкт з
  ключами-ідентифікаторами сторінок; кожне значення перелічує елементи сторінки з `kind`, `name`,
  `owner`, `signature`, `start_line`/`end_line`, `doc`, `doc_text` (уся документація одним рядком,
  коли вона довша за `doc`; для ранжування, не показується), `public`, `test` (тестовий код), `twin`
  для парного C++-оголошення чи визначення, а для функції — `calls` (`path:start-end` функцій, які
  вона викликає) і `call_lines` (для кожної — рядки виклику). Виклики shell-файлу поза функціями
  належать елементу `top_level`.
- **`llms.txt`** — сторінки з PageRank не нижче медіани під `## Docs`, решта під `## Optional`.
  Кожен рядок несе опис сторінки, обрізаний до 160 символів.
- **`AGENTS.md`** — з чого почати, як отримати сусідів чи карту символів модуля, і що розділ
  `## Notes` кожної сторінки зберігається між перекомпіляціями.

### Obsidian і Quartz

Посилання, які пише компілятор, — це вікі-посилання Obsidian з явною ціллю,
`[[slug|Display Name]]`, а кожен `<slug>.md` — справжня сторінка, тож вони працюють без плагінів,
а граф і зворотні посилання в Obsidian діють. Відкривайте як сховище саму теку з результатом
компіляції, а не батьківську, де лежать і джерела: їхні імена файлів можуть збігтися зі
сторінками. Quartz читає ті самі посилання: [`scripts/`](../../scripts/README.md) публікує скомпільовану
вікі як сайт на Quartz.

Кожна сторінка починається з YAML front matter, тож Obsidian показує її властивості: `created`,
`updated`, `aliases`, `tags`, `kind`, `source` і `source_hash`. `tags` починається з тега виду
(`wiki/code`, `wiki/doc` або `wiki/memory`), далі йдуть теги самої нотатки. `## Body` сторінки коду —
огороджений блок з мовою, тож коментарі, `#include` і `<T>` рендеряться як код. Щоб розфарбувати
граф за видом, додайте групи в Graph view > Groups із запитами `tag:#wiki/code`, `tag:#wiki/doc` і
`tag:#wiki/memory`. Компілятор не пише конфігурацію `.obsidian/`.

Власні посилання нотатки чи документа переписуються так, щоб Obsidian знаходив ціль (тіла кодових
сторінок у блоці коду, їх не чіпають): `[[Matching Engine]]` стає `[[matching_engine]]`, якщо така
сторінка є, а відносне Markdown-посилання на проіндексовану сторінку, як-от
`[guide](../docs/guide.md)`, стає `[guide](guide.md)`. Решта посилань лишається як є й
показується нерозвʼязаними вузлами (у цьому репозиторії — `LICENSE`). `#`, який Obsidian прочитав би
як тег, наприклад `#76→`, екранується як `\#`.

### Ідентифікатори сторінок

Ідентифікатори сторінок (і назви файлів) відповідають `[a-z0-9_]+`. Вони утворюються з назви кожного
джерела: розділові знаки й пробіли згортаються в `_`, латинські літери з діакритикою — до базової, а
кирилиця транслітерується (`Морський маяк` стає `morskyi_maiak`). Сторінка `mod.rs` чи `__init__.py`
називається за своєю текою (`tests/common/mod.rs` → `common`). Дві назви, що згортаються в один
ідентифікатор — `Fetch (v2)` і `Fetch v2`, два файли з однаковою основою в різних теках,
`orderbook.h` і `orderbook.cpp`, — розрізняються сегментом теки, потім розрізнювачем з назви файлу,
потім вільним ідентифікатором; жодне джерело не губиться через збіг
([докладніше](docs/ARCHITECTURE.md#disambiguation-ladder)). Назва, у якій після згортання не
лишилося жодної літери чи цифри, стає `page_<hash>`. Ідентифікатор, що мав би бути `index`, `llms`,
`agents` чи `graph`, стає `<id>_page`, бо це імена власних файлів вікі; `compile` про це попереджає.

## Виміряне

Контрольні виміри синтетичні: завдання, написані для вимірювання, а не реальна робота. В єдиному
спостережуваному живому проєкті перед 90–98% читань файл уже названо в завданні, і сильні моделі й
так читають вузько. Чи типовий цей проєкт, ми не вимірювали.

52 з 52 нижче виміряно з власними інструкціями сервера, що велять агентові користуватися `wiki` перед grep (їх `wiki setup` лишає для Claude Code), і з абзацом у `CLAUDE.md` проєкту про те, щоб спершу користуватися ним, — його `wiki setup` не пише. Завдання пошуку нічого не казало про інструменти; завдання правки повторювало вказівку. Це
власні виміри авторів їхнього інструмента, на завданнях і дереві коду, які вони обрали. Будемо
раді, якщо ви долучитеся до вимірювань: запустіть `wiki` на своєму проєкті та
[відкрийте issue](https://github.com/bambooplanedev/nollm-wiki/issues) з тим, що побачите, — цифри, добрі чи погані.

Кожен блок нижче називає власні умови, і його цифри чинні лише там: що модель зробила на цих
задачах у цьому дереві, а не що `wiki` зробить у вашому. Головний README набору підсумовує їх у

Ранжування 0.5.0 ставило нотатку першою в 51 із 60 code-запитів; хвіст не міняє жодного рядка
коду. Haiku потребує воріт у чотири літери: при восьми його короткі кодові запити не показували
нотатку в 14 із 60 прогонів (42/60 правильно). Ціна воріт на кодовій роботі (Haiku, 12 code-задач
без нотатки про них, з 42 нотатками про інші проєкти, 36 прогонів): чужа нотатка в 27 прогонах,
жодної не відкрито, 36/36 правильно, 74 прочитані рядки проти 83 без нотаток, близько 340 байт
більше на відповідь пошуку. Рядок hook не міняє відповідей на Haiku (49/60 з ним і без) і
економить один пошук на задачу; у довгих промптах він називає нотатку лише до 64 різних слів
(раніше нотатку показували 53 із 58 довгих промптів, тепер 5), короткі питання без змін.

## Обмеження

- **Зіставлення лексичне.** Ні ембедингів, ні семантичного пошуку: «credentials» не знаходить `creds`.
  Текстова чи Markdown-сторінка звʼязується, коли її назва чи псевдонім трапляється на іншій
  сторінці; сторінка коду — лише через згадку її модуля у вигляді коду (шлях з `::`, оголошення
  `mod`, назва файлу), імпорт або відносне Markdown-посилання.
- **Виклики розвʼязуються за іменем і кількістю аргументів**, у межах однієї мови, без типів: метод,
  викликаний на значенні невідомого типу, веде на всі однойменні методи, які бачать файли
  викликача.
- **Три формати.** Текст, Markdown і код; без PDF, OCR і аудіо.
- **MCP-сервер лише для запитів**, через stdio; перекомпільовує після правок файлів, а не на запит.
- **Граф експортується лише в JSON.**

Виміряні недоліки й поведінка агентів: [docs/KNOWN_GAPS.md](docs/KNOWN_GAPS.md).
Внутрішня будова, правила детермінізму й як додати мову: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
Обидва документи англійською.

## Бібліотека

CLI — тонка обгортка над тим самим API:

```rust
use std::path::Path;
use wiki::{compile, CompileOptions};
use wiki::query::{Wiki, PackBudget};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let opts = CompileOptions { incremental: true, ..Default::default() };
    let result = compile(Path::new("demo_raw"), Path::new("demo_wiki"), &opts)?;
    println!("{} pages compiled", result.pages_total);

    let wiki = Wiki::load(Path::new("demo_wiki"))?;
    for hit in wiki.search("gradient", None, 5) {
        println!("{}\t{}", hit.id, hit.title);
    }
    let budget = PackBudget { max_tokens: Some(2000), ..Default::default() };
    if let Some(pack) = wiki.neighbors("some_id", 1, &budget) {
        println!("{}", pack.text);
    }
    Ok(())
}
```

`CompileOptions.project` (у CLI — `--project`) задає назву проєкту в `index.json`, `llms.txt` і
`AGENTS.md`; за замовчуванням це остання частина шляху вхідної теки. Крім `search` і `neighbors`,
`Wiki` має `page(id)` (Markdown готової сторінки), `has_page(id)` і `list_pages()` (пари
`(id, title)` за зростанням id).

## Розробка

### Збірка

З кореня робочого простору:

    cargo build --release      # target/release/wiki
    cargo test                 # модульні, інтеграційні, snapshot-тести й оцінка пошуку; потрібен jq
    cargo clippy --all-targets -- -D warnings
    cargo fmt --check

### Самохостинг

Цей репозиторій компілює сам себе. `scripts/selfhost.sh` збирає релізний бінарник, компілює
репозиторій у `.nollm-wiki/` (у gitignore, інкрементально) і запускає на ньому `wiki lint`; на битому
посиланні скрипт завершується з помилкою. Закомічений `.mcp.json` реєструє `wiki serve --source .` як сервер `wiki`, тож
агент, запущений тут, може шукати в проєкті; у свіжому клоні запустіть `scripts/selfhost.sh` один
раз, щоб бінарник зʼявився.
